# MiniMax Code：配置刷新、自动压缩与 Ask-user 复核

回应 User seq17，只复核这三项，不扩大到已降低优先级的七项资格矩阵。
实现基线 `c2640d0176b7345a57102bbaf97cd5c870e02b36`，实际 mcode 0.6.12 / macOS arm64。
本轮使用生产 Core、隔离 data/Skill Library/MCP/native profile 和真实 Sub2API `gpt-6`。
原有开发 App 保留；本轮不修改 Runtime 实现、用户原生配置、Fast 或 First-Class 准入。
结构化结果见[脱敏证据](followup-2026-10-16.evidence.json)。

## 1. 外部 Auth/Provider 配置：先比较，再判断是否需要摘要

下表覆盖全部 19 个 Adapter identity。其他 18 款是当前分支代码审计，没有在本轮逐一重跑原生刷新。
“无额外摘要”仅指原生凭据/Provider 文件内容；共同的程序、启动环境、权限、工作区和 MCP
兼容性判断仍存在。不能据此推断这些 Runtime 都会热刷新，或都不会热刷新。

| Runtime | Rovai 的进程/配置兼容性处理 | 对 MiniMax 的参照意义 |
| --- | --- | --- |
| MiniMax Code | 共享 ACP/Fleet，无独立 native Auth/Provider 内容摘要 | 本轮真实下一 Run 读取新地址和 Key，同 Host、同 Session |
| Codex、Pi | 驻留 Host；共享启动配置摘要，没有在对应 Host 摘要额外读取原生凭据文件内容 | 不是所有驻留 Runtime 都依靠额外文件摘要 |
| OpenCode、Copilot、Qoder、CodeBuddy、Qwen、TRAE、Kimi | 共享 ACP 兼容性；没有上述 Auth/Provider 文件内容摘要分支 | OpenCode 的 generation/storage 兼容键、TRAE 的恢复兼容键不等于凭据文件监视 |
| DSH、Grok、Command Code、Cline、ZCode | 有各自 native configuration digest，进入 Host 兼容性；恢复另按各自规则处理 | 这是针对原生实现的适配，不应无条件照搬到 MiniMax |
| Claude Code、Antigravity | 每 Run 新进程，恢复精确 Session | 不具有同样的跨 Run 驻留进程配置陈旧问题；不代表运行中配置立即改变 |
| Kiro、Cursor | 当前正常 release 为 Stop；Cursor 不承诺 Host warm reuse | 同样不适合作为“必须加配置 watcher”的依据 |

依据：[ACP compatibility/release](../../../crates/rovai-core/src/acp.rs)、
[Codex](../../../crates/rovai-core/src/codex.rs)、[Pi](../../../crates/rovai-core/src/pi.rs)、
[OpenCode storage compatibility](../../../crates/rovai-core/src/opencode_compat.rs)和
[Adapter Host projection](../../../crates/rovai-core/src/agent_runtime_adapter.rs)。

真实刷新 Probe 在同一 `custom_provider:rovai-auto` 上修改 `options.baseURL` 与 `options.apiKey`：

1. 原生请求到 loopback relay A，携带合成 Key A；relay 用已有授权凭据转发真实 Sub2API。
2. Host 空闲时，外部修改隔离 YAML，改为 relay B 与合成 Key B。
3. 下一 Run 的真实模型请求到 B，Key B 匹配；Host PID 42117 不变，Native Session
   `mvs_8bb3caf6716d41b9a09ed2a1c69f4ac2` 不变。A/B 的真实 upstream 账号没有轮换。
4. 独立开关 Probe 中，外部写入 `askUser.enabled: false` 后，下一 Run 的原生工具清单已移除
   `ask_user`，Host PID 41454 与原 Session 不变。

这证明 **Rovai 当前调用路径下，已选 Provider 的地址/Key 与 askUser 开关能在下一 Run 生效**。
Rovai 每次配置 MiniMax Run 会调用原生 `permissionMode` config option；上游权限配置路径存在
读取、更新配置并清除缓存的逻辑。单独看到 `getConfig()` 缓存不足以认定整条路径不会刷新。
不将该结果扩大成运行中即时刷新、OAuth 换号、任意原生配置或全局默认 Provider 切换资格。
既有 Session 保留已选模型是此前已验证的原生行为；切换全局默认不等于重置 Session 模型。

**结论修正：撤回把“缺少 MiniMax 专属配置摘要”列为优先缺陷的判断。保持现有 Host 复用和
精确 resume；本轮证据不要求再加 watcher、私有冻结层或新摘要。**

## 2. 自动压缩：真实生产 Core 路径已触发

通过官方 Provider 配置把本次独立 profile 的上下文设为 65,536、输出上限 4,096。
按[原生预算公式](https://github.com/MiniMax-AI/minimax-code/blob/9a935605956c4500e9cb415f29258e2887e97817/packages/agent-modules/context-manager/src/provider-budget.ts)
预期触发阈值为 49,152。连续发送三轮惰性合成数据，每轮仍由真实模型执行 bundled `rovai send`。
没有发送 `/compact`、没有伪造 Usage、没有修改原生 Session 或压缩记录。

| 证据 | 实测 |
| --- | --- |
| 原生提交 | history generation 0→1→2，两个不同的 `compactionSummary` message ID |
| 压缩前 tokens | 第一次 58,388；第二次 56,911；来自原生 `tokensBefore` |
| 同一 Run | 第三轮填充 Run `fd8be52d-02c4-421a-91ee-7b173e93de9f` 内发生两次自动压缩，Run 成功 |
| 压缩后首个模型输入 | 第二次后首次主模型调用为 44,002 input tokens（input + cacheRead）；这是调用用量，不是独立 compaction-after 计数 |
| Host/Session | 成功基线、三轮填充、连续性检查均 PID 40301；Session `mvs_d45aab1abd4b4bd48e5ad26bcb5340c6` 不变 |
| Bootstrap | 每次原生主模型请求系统层 Charter 恰好一份；前后 Bootstrap SHA-256 相同 |
| 早期上下文 | 后续输入没有重复标记，也没有查历史文件；实际公开消息为 `ORCHID-4821-TEAL AUTO_CONTINUITY_OK` |
| 公开发送 | 压缩所在轮与后继轮均有真实 CLI send 回执和 Core 持久化消息 |

第一个 summary 在第二次压缩后进入原生 snapshots；不能只数 active messages 中最后一个 summary
就声称只发生一次。输入含大量重复数据且原生保留近期上下文，不能把这个样例的压缩率当通用指标。

本轮补齐 **threshold 自动压缩 + 同 Host/Session 连续性**。它不是默认大窗口阈值资格、
provider overflow+retry 或取消/失败矩阵；没有新增 MiniMax 手动按钮或压缩生命周期展示。
上轮的 manual compact + App/Core cold resume 证据继续单独保留。

## 3. Ask-user：建议默认关闭，已复现具体失败

官方[开关定义](https://github.com/MiniMax-AI/minimax-code/blob/9a935605956c4500e9cb415f29258e2887e97817/packages/config/src/ask-user-config.ts)
默认 `enabled: true`，可用原生 `askUser.enabled: false` 关闭。关闭后工具实际不再暴露，
不是仅靠提示词要求模型不要调用。

在启用状态下，真实模型按验收指令调用 `ask_user` 一次，提交无真实业务含义的颜色选择题。
原生返回“等待本地用户”，但 `questionnaire_requests` 在 1 ms 后记录 `dismissed`，
`answered_at`、`reply_payload`、`injected_at` 均为空。Core 没有生成问卷审批；该 Run
`64862b52-d4b0-4c9c-b15f-32615a5fe1bd` 以 `runtime_missing_final_output` 结束。
关闭后后继 Run 恢复正常发送；冷恢复仍为原 Session。

原因与[官方 ACP interaction 实现](https://github.com/MiniMax-AI/minimax-code/blob/9a935605956c4500e9cb415f29258e2887e97817/packages/tui/src/acp/interactions.ts)
及[问卷 normalization](https://github.com/MiniMax-AI/minimax-code/blob/9a935605956c4500e9cb415f29258e2887e97817/packages/local-runtime/src/questionnaire/normalize.ts)
一致：Rovai 没广告 elicitation/form；原生仅把有限的单选题回退成 permission，而当前题目强制
`allowOther: true`，不符合该回退条件，最终 dismiss。**本次没有自动代选第一项**。
通用免审批处理确实会选第一项 `allow_once`，但不能把潜在的简单题回退风险写成本次已发生的故障。

| 其他 Runtime 的当前实现 | 与建议的关系 |
| --- | --- |
| Pi | 不支持的 Extension UI 返回 cancelled，confirm 返回 false |
| Cursor | `cursor/ask_question` 明确返回 skipped；Plan Review 返回 rejected |
| ZCode | 启动声明 `askUserQuestionAutoResolutionEnabled: false`，关闭的是自动解答，不等于移除问卷工具 |
| Claude Code | 当前未发现统一禁止 `AskUserQuestion` 的启动策略；不能宣称所有 Runtime 已统一关闭 |

建议 Rovai 中默认关闭原生问卷工具，必要问题走 Thread 的公开提问和 User 正常回复。
工具执行的权限审批仍走现有机制。此处是建议，不冒充已经实施产品默认关闭。
当前 mcode ACP help 没有独立进程级禁用工具/config overlay 参数；不为这一开关复制原生 Home、
凭据或 Session，也不直接修改 User 全局 YAML。后续产品落地应先选择官方支持的局部配置接缝。

## 尝试记录与范围

- 自动压缩首个基线 Run 已公开发送，但模型以空 final 结束，被 Core 标记
  `runtime_missing_final_output`。保留该失败；后续明确要求非空 final，同 Session 继续成功。
- Ask-user 第一次采集脚本把原生 custom message 的 content 当数组，采集失败；修正为类型检查后重跑。
  该错误属于验收脚本，不是 Runtime 故障；原始记录保留在隔离诊断目录。
- 后来的真实 ask_user Run 失败独立记账，没有用关闭开关后的成功覆盖。
- 凭据、原始系统提示、加密推理字段及原始 Session 不进入公开证据。临时 Core/Runtime/relay 均已退出，
  新复制的临时凭据按隔离流程清理，之前留给 User 的开发 App 不关闭。
